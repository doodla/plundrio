# v0.10.13

## What changed

The post-complete retention janitor — the deferred-cleanup safety net that purges put.io transfers when the *arr client never issues `torrent-remove` — now actually runs. Since v0.10.11 shipped the design, it has been a silent no-op in every default deployment.

## Why

`cmd/plundrio/main.go` registered the CLI flag as `post-complete-retention` (hyphens, Cobra convention) but read it back via `viper.GetDuration("post_complete_retention")` (underscores, YAML/env-var convention). `viper.BindPFlags` keys flags under their literal flag name; `SetEnvKeyReplacer` only rewrites env-var lookups, not the in-memory key used by `GetDuration`. With no `PLDR_POST_COMPLETE_RETENTION` env var and no config file, the lookup missed the flag default, returned `Duration(0)`, and `purgeStaleProcessed` short-circuited at `if retention <= 0 { return }`. 24-hour fallback purges never fired.

Observed in production on `doodle-nas` after v0.10.12 ran for a week: 10 transfers reached `Transfer processed` between 2026-05-06 and 2026-05-07, all crossed the 24h retention cutoff, zero `purge` log lines fired, put.io's 100 GB quota filled to 190 GB and locked the queue.

## How the fix is shaped

- `config.Config` gains `mapstructure` tags. The struct is now the single source of truth for key names — YAML, env-var-after-replacement, and the explicit per-flag bindings all converge here.
- `cmd/plundrio/main.go` extracts a `loadConfig(cmd)` function that binds each cobra flag to its canonical viper key via `viper.BindPFlag`, then decodes the whole surface via `viper.Unmarshal`. The per-key `viper.GetString/GetInt/GetDuration/GetBool` calls are gone.
- A new `flagViperBindings` map carries the (hyphenated flag name → underscored viper key) translation explicitly so the asymmetry is visible and reviewable in one place.
- `TestLoadConfigDefaults` + `TestLoadConfigEnvOverride` + `TestLoadConfigConfigFile` + `TestFlagViperBindingsCoverAllRunFlags` in `cmd/plundrio/config_test.go` cover all three config-resolution paths and assert defaults survive an empty environment. A future flag added without a binding entry now fails the test, not production.
- The startup `Configuration loaded` log promotes from Debug to Info so the resolved retention value is visible in `docker logs` on first start without flipping log level.

## Visible behavior

- `docker logs plundrio` now prints a `Configuration loaded` INFO line at startup with `post_complete_retention=24h0m0s` (default) or whatever the operator set.
- After ~24h post-deploy (or sooner with `PLDR_POST_COMPLETE_RETENTION=<shorter>`), put.io transfers in `Processed` state that never received a `torrent-remove` get cleaned up automatically: per-transfer `purge` INFO lines fire (`Deleted source file`, `Deleted transfer`).

## Migration / unblock

The fix doesn't retroactively rescue transfers stuck before the upgrade. Container restart re-discovers them as healthy COMPLETED transfers on put.io, walks `processTransfer` against the already-on-disk files, and stamps `processedAt = time.Now()` — restarting the 24h clock. Operators with a quota-locked put.io can either wait 24h post-deploy or manually delete the stuck transfers via the put.io API to unblock immediately.
