# v0.10.11

## What changed

plundrio no longer deletes a put.io transfer the moment local download finishes. The transfer now stays visible in `torrent-get` as Seeding/100% until either the *arr client issues `torrent-remove` (the normal path) or a configurable retention window elapses (safety net, default 24h).

## Why

Sonarr/Radarr's `TrackedDownloadService` requires a torrent to remain in `torrent-get` between polls until the client itself removes it. When the entry vanishes mid-flow, `IsTrackable` is set to `false` with no `DownloadFailedEvent` and no on-disk fallback — the file ends up orphaned on disk with no import. With Radarr's 60s default poll and plundrio's previous sub-second cleanup, the catch window was a deterministic miss for some grabs that completed via the local-retry cascade.

## Visible behavior change

If you run with `RemoveCompletedDownloads=false` on the Radarr/Sonarr download-client config (or you manage put.io transfers without an *arr client at all), completed transfers will now linger on put.io for up to `PostCompleteRetention` (default 24h) before plundrio cleans them up unilaterally. Set `--post-complete-retention 0` (or `PLDR_POST_COMPLETE_RETENTION=0`) to keep the previous "wait for the client forever" behavior — at the cost of a slow put.io quota leak if the client never removes anything.

For the typical setup (`RemoveCompletedDownloads=true`, the default), the user-visible impact is zero: the *arr issues `torrent-remove` within seconds of import.

## New configuration

| Flag | Env | YAML | Default |
|---|---|---|---|
| `--post-complete-retention` | `PLDR_POST_COMPLETE_RETENTION` | `post_complete_retention` | `24h` |

Accepts any Go `time.Duration` string (e.g. `30m`, `2h`, `48h`). `0` disables the janitor.

## Internal

- New `Manager.PurgeTransfer` consolidates three previously-divergent put.io-delete paths: `handleTorrentRemove`, the orphan-recovery branch of `handleTransferError`, and the new retention janitor.
- The FileID==0 cascade-delete-root protection (originally added in #25 for `handleTorrentRemove`) now lives inside `PurgeTransfer`. Single source of truth.
- `processedTransfers` map (used for log visibility) is now cleaned up on purge, plugging a slow leak.

## No migration needed

Container restart picks up the new behavior. No state file changes, no schema changes. Settings carry over.
